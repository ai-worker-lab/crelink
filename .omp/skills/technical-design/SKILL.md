# 기술 설계와 티켓 분해 절차

흐름, 역할, 분해 규칙, 문서 상태는 `docs/specs/README.md`가 기준입니다. 이 스킬은 그 안에서 일하는 순서입니다. 설계 승인과 미정 사항 결정은 사용자가 합니다.

## 디자인 기술 검토 (디자인 승인 전)

1. `design/<기능>/`(인계 전이면 OpenDesign 프로젝트를 `get_artifact`로)와 PRD를 읽습니다.
2. 화면마다 확인합니다.
   - 보여 주는 데이터를 어떤 API·테이블에서 얻는지, 새로 만들어야 하는지
   - 상태가 빠지지 않았는지: 로딩, 빈 상태, 오류(네트워크·권한·검증), 권한 없음, 긴 텍스트·많은 항목
   - 플랫폼 제약: Expo/React Native에서 같은 상호작용이 되는지, 웹 서버 컴포넌트·BFF 경로로 가능한지, 오프라인·백그라운드 동작
   - 디자인 토큰 밖의 값(새 색·간격)이 필요한지
3. 걸리는 점을 `docs/specs/<에픽 slug>.md` 초안의 `디자인 검토 의견`에 쓰고 `designer`에게 돌려보냅니다. 막는 문제가 없으면 "기술 검토 통과"와 남은 주의점을 적습니다.

## 설계 작성

1. 입력을 모읍니다: 확정 PRD(`[사용자 확정]` 요구 목록), `handoff.md`, 기술 조사·ADR, 관련 코드(`packages/shared`, `apps/api/src`, 웹·앱 API 클라이언트, migration). 입력이 확정되지 않았으면 무엇이 빠졌는지 보고하고 멈춥니다.
2. `docs/specs/TEMPLATE.md`를 복사해 `docs/specs/<에픽 slug>.md`를 만들고 `상태: 초안`으로 둡니다.
3. **요구 대응표**부터 채웁니다. 모든 `[사용자 확정]` 요구가 화면·API·데이터·티켓 중 하나 이상에 나타나야 합니다.
4. 데이터 모델, API 계약 초안, 화면 상태와 API 대응, 권한·개인정보, 비기능을 채웁니다. 기존 코드의 패턴(오류 형식 `ApiError`, BFF 경로, migration 실행 방식)을 따르고 새 패턴이 필요하면 ADR 후보로 적습니다.
5. 답을 모르는 질문은 `위험과 스파이크`로 옮기고, 그 답에 기대는 티켓을 표시합니다.
6. **티켓 분해안**을 `docs/specs/README.md#분해-규칙`대로 작성합니다: 계약 티켓 → 병렬 구현 티켓 → 통합 티켓, 스파이크, 역할 하나씩, 진짜 의존만 선행, 수용 기준마다 확인 방법.
7. **검증 계획**에 에픽 통합 수용 기준과 E2E 시나리오(PRD 사용자 시나리오 단위)를 적습니다.

## 검토 위임

`task`로 역할별 검토를 한 batch에 병렬로 맡깁니다. 검토자는 설계 문서를 고치지 않고 의견만 돌려줍니다.

| 대상 | 맡길 질문 |
| --- | --- |
| `api` | 계약·데이터 모델·권한이 구현 가능하고 기존 패턴과 맞는가, 오류 코드가 충분한가 |
| `web`·`app` | 화면 상태와 API 대응이 빠짐없는가, 플랫폼 제약이 있는가 |
| `infra` | 새 인프라 의존이 있을 때만 |
| `designer` | 화면 상태·상호작용이 디자인 인계와 맞는가 |
| `product` | 요구 대응이 PRD와 같은 범위인가, 빠진 요구가 없는가 |

의견을 `검토 기록`에 남기고 본문에 반영합니다. 상충하는 의견이나 제품 결정이 필요한 것은 `미정`으로 올립니다. 반영이 끝나면 `상태: 검토`로 바꾸고 사용자에게 승인을 요청합니다(바뀐 점, 미정 질문과 선택지).

## 승인 후 티켓 분해

1. 사용자가 승인하면 `상태: 승인`, 관련 ADR을 `승인`으로 바꿉니다.
2. 에픽 work item(`연결`에 설계 문서·PRD)과 분해안의 티켓을 `docs/work/TEMPLATE.md`로 만듭니다. 에픽은 `docs/work/epics/`, 티켓은 `역할` 폴더 `docs/work/<역할>/`에 두고, 번호는 모든 폴더를 통틀어 다음 빈 번호부터 씁니다. 각 티켓의 `연결`에 설계 문서 절 링크와 요구 번호(R1…)를 적고, 수용 기준은 분해안의 확인 방법을 옮깁니다.
3. 바로 착수할 티켓(계약·스파이크)만 `준비`로, 나머지는 선행이 걸린 채 `준비`로 두거나 스파이크 결과를 기다리는 것은 `분류 대기`로 둡니다. `pnpm work:check`, `pnpm work:next --all`로 순서와 착수 가능 목록을 확인합니다.
4. 설계 문서의 `예정` 번호를 실제 번호로 바꿉니다.

## 진행 중

- 구현 중 설계와 다른 결정이 필요하면 해당 티켓 담당이 `진행 기록`에 적고 `orchestrator`에게 알립니다. 설계 문서 `변경 기록`에 반영하고 영향받는 티켓을 갱신합니다.
- 통합 티켓에서 검증 계획을 실행하고, 결과를 에픽 `진행 기록`에 남깁니다.
