# ADR 0003: work item 3단계(에픽·티켓·하위 티켓)

- 날짜: 2026-10-01
- 상태: 승인 (결정 4의 폴더 부분은 [ADR 0009](0009-work-item-role-folders.md)가 대체: 계층은 여전히 필드, 파일은 역할별 폴더)
- 범위: 저장소 전체 (ALM 작업 관리)

## 배경

- [ADR 0002](0002-work-items-in-repository.md)로 work item을 `docs/work/`의 Markdown 파일로 관리하기로 했습니다. 처음 형식에는 계층이 없어 GitHub의 Epic·Issue·Sub-issue 같은 분류를 표현할 수 없었습니다.
- 사용자는 에픽을 최상위로 두고, 그 아래를 역할별 작업과 그 세부 작업으로 나누기로 했습니다.
- 이 저장소는 `.omp/agents`의 역할(api·web·app·infra·designer·product·orchestrator)별로 소유 경로를 나눠 병렬 위임합니다([영역별 병렬 개발](../development/parallel-work.md)).

## 결정

1. work item은 `에픽` → `티켓` → `하위 티켓` 3단계입니다. 에픽은 사용자에게 보이는 결과, 티켓은 한 역할의 작업, 하위 티켓은 티켓의 세부 작업입니다.
2. 중간 단계 이름은 "티켓"으로 합니다. "issue"는 사용하지 않는 GitHub Issues와, "task"는 OMP `task` 도구·`.omp/config.yml`의 `task` 설정과 혼동되기 때문입니다.
3. 티켓과 하위 티켓은 `역할` 필드에 agent 이름 하나를 가지며, 한 티켓은 한 역할의 소유 경로만 바꿉니다. 사용자 관점의 수용 기준과 영역 간 통합 검증은 에픽에 둡니다.
4. 계층은 폴더가 아니라 자식 파일의 `상위` 필드, 역할 간 순서는 `선행` 필드로 표현합니다. 부모 파일에 자식 목록·진행률을 적지 않습니다.
5. 사용자 가치 단위가 아닌 결함·유지보수·운영·제품 결정은 상위 없는 독립 티켓으로 둡니다.
6. 규칙 검사와 트리·진행률 출력은 `scripts/work.mjs`(`pnpm work:check`, `pnpm work`)가 맡습니다. 세부 규칙은 [작업 관리](../work/README.md)가 기준입니다.

## 결과와 트레이드오프

- 티켓 하나를 해당 역할 agent에 그대로 위임할 수 있고, 에픽은 통합 검증의 책임 위치가 됩니다.
- 역할로 나누면 에픽 하나에 파일이 여러 개 생깁니다. 하위 티켓은 별도 상태·검증·커밋이 필요할 때만 만들어 파일 수를 억제합니다.
- 진행률·트리는 GitHub 화면이 아니라 명령 출력으로 봅니다. 부모 자동 완료는 없고, 검사가 "자식이 남은 완료 부모" 같은 모순을 실패로 잡습니다.
- 여러 영역을 바꾸는 독립 작업은 `orchestrator` 티켓이 되어 역할 분리가 느슨해집니다. 범위가 커지면 에픽과 역할별 티켓으로 나눕니다.
- 티켓을 처리하는 주체는 `역할`의 agent입니다. 1인 개발이라 사람 담당자는 항상 같으므로 별도 `담당자` 필드를 두지 않습니다. 사람의 결정은 `종류: 제품 결정`과 `(AI 제안)` 표시로 구분하며, 협업자가 생기면 `담당자` 필드 추가를 다시 검토합니다.
