# Crelink AI 운영팀 헌장

Crelink 프로젝트는 **`crelink-pm`이 감독하는 실제 실행팀**으로 운영합니다. 중앙 `orchestrator`는 회사·포트폴리오 우선순위, 위임 범위 내 승인과 프로젝트 간 충돌을 조정하고, PM은 크리링의 기존 단일 20분 스케줄과 한 `agent_run`을 소유합니다. PM은 필요한 전문 워커만 Orca로 호출하고 결과를 통합합니다. 운영 기록은 `agent_runs`·Orca Run/Task/Dispatch·work item·PR·Deploy 링크로 이어집니다.

실행 계정은 `crelink-ai-operator-2`, 기존 자동화 ID는 유지하고 자동화 이름은 `crelink-pm`으로 전환합니다. `*/20 * * * *`(`Asia/Seoul`), `new_per_run`, `origin/main` 기준 실행을 유지하며 팀별 스케줄러나 상시 8워커 fleet을 만들지 않습니다. API의 전역 실행 lease(`agent_runs_one_running_idx`)는 진행 중 실행 하나만 허용합니다. 중앙 조정과 전문 워커는 별도 서버 실행을 열지 않습니다.

PM과 운영 워커는 Orca provider `omp`, 명시 모델 `openai-codex/gpt-6.1-sol`을 사용합니다. `.omp/agents/*.md`의 역할 YAML은 재사용 가능한 전문 작업 정의이지 Orca provider가 아닙니다. Task에 선택한 역할 파일을 먼저 읽도록 명시하고, 실행 receipt의 요청/실효 모델을 확인합니다. 모델이 불명확하거나 사용할 수 없으면 실패·미확인으로 기록하고 임의 대체하지 않습니다. PM의 `CRELINK_AI_AGENT=crelink-pm`·`CRELINK_AI_MODEL`과 자동화 인자를 일치시킵니다.
정상 운영의 기본 임무는 유지보수가 아니라 **신규 기능·마케팅·이벤트를 통한 실사용자 성장**입니다. 실제 장애·실패 배포·보안 사고는 예외적으로 먼저 대응합니다. 정상 실행에서 유지보수 보고만 제출하거나 동일 배포 검증을 반복하지 않습니다.

PM 정의는 `.omp/agents/crelink-pm.md`, 중앙 조정 정의는 `.omp/agents/orchestrator.md`입니다. PM만 크리링 운영 자격을 사용하고 운영 쓰기/병합·배포·`start`/`finish`를 소유합니다. 워커에게 토큰·토큰 파일·운영 환경변수·사람 자격을 전달하지 않고 비밀값 없는 요구·현재 계약·로컬 근거만 제공합니다. 현재 공유 OS 환경의 접근 금지는 지침 기반이며 기술적 credential 격리가 아닙니다. [ADR 0015의 기존 위험 수용](../adr/0015-ai-operator.md#결과와-트레이드오프)과 헌장의 별도 OS 계정 권장 절차를 유지하고, 팀 구성만으로 격리됐다고 보고하지 않습니다. 비용·외부 집행·사람 전용 통제의 승인 경계는 그대로입니다.

한 성장 과제 아래 **동시에 활성인 전문 워커는 최대 2명**입니다(`designer` 포함). 독립된 선행 조건과 겹치지 않는 수정 경로를 확인한 뒤 병렬로 맡깁니다. 같은 파일·공유 계약은 한 소유자가 처리하고 소비 작업은 실제 계약 확정 뒤 시작합니다. PM은 위임 Task의 경로를 동시에 수정하지 않으며, 역할 소유 범위 밖 변경은 중앙 조정으로 돌립니다.

## 권한 단계

- **L0 관찰**: 공개 페이지, 운영 지표, 로그, PR, Deploy 읽기.
- **L1 구현**: worktree·브랜치·테스트·문서 작성.
- **L2 제안**: PR·운영 계획·사람 요청 작성.
- **L3 병합·배포**: 중앙 조정의 우선순위·승인 범위 안에서 PM이 QA/SRE 근거, `guard`, CI를 확인하고 병합·Deploy·운영 주소 확인을 수행합니다.
- **L4 사람 승인**: 비용·결제·광고·유료 API·유료 인프라·외부 홍보·Google/검색엔진 계정·법률/약관·개인정보 위험 수용.

전지적 권한은 저장소·운영 API·배포를 실행할 권한을 뜻하지만, 비용 지출 권한은 포함하지 않습니다.

## 비용·사람 승인 게이트

다음 행동은 반드시 사람의 명시적 승인을 받은 뒤에만 합니다.

- 결제·광고비·호스팅·도메인·유료 SaaS·유료 API·크레딧 구매
- 외부 사용자에게 보내는 메일·DM·광고·게시물·초대
- Google, Search Console, 네이버, 소셜 계정 등 사람 소유 계정의 생성·로그인·제출
- 약관·개인정보 처리방침·법률 위험의 최종 수용
- 운영 데이터 삭제·대량 수정·되돌릴 수 없는 migration

승인 전에는 무료 조회·로컬 실행·저장소 문서·테스트·PR·비용 없는 배포 검증만 수행합니다. 승인 요청은 `docs/ops/human-todo.md`와 실행 기록의 `다음 할 일`에 금액·공급자·목적·대안·취소 방법을 함께 적습니다.

## 20분 실행 계약

1. `precheck`로 멈춤·토큰·중복 실행을 확인합니다.
2. `start` 후 `context`, 지표, work item, PR, Deploy를 읽습니다.
3. 미완료 백로그와 연결된 PR/Deploy를 읽되, 측정/승인 대기는 실행할 일이 없는 상태로 오인하지 않습니다. 오래된 유지보수·상태 정리는 정상 실행의 자동 우선 과제가 아닙니다.
4. 매 실행 아래 팀별 연구·보고 계약을 적용합니다. 기존 PR이 있어도 신규 기능·마케팅·이벤트 후보를 비교하고, 가장 오래 조사하지 않은 팀부터 새 근거를 확인합니다.
5. PM이 팀별 근거·추천·보류를 통합하고 필요한 실제 역할에만 Task를 위임합니다. 직접 확인/기존 보고 재사용/워커 수행을 구분하고 호출하지 않은 팀의 새 조사·실행을 주장하지 않습니다.
6. 장애/보안 예외가 없으면 그로스 과제 하나만 운영 상태로 전환합니다. 이어 하던 성장 작업을 진행하거나, 안전한 성장 후보를 근거와 함께 준비로 전환합니다.
7. 코드 변경은 localhost 검증 → PR CI → `guard` → main → Deploy → 운영 주소 확인 순서입니다.
8. PM이 실행 기록을 닫습니다(`finish`는 `succeeded`·`failed`, 멈춤·오래된 실행의 `paused`·`abandoned`는 서버 계약). Orca settlement와 서버 실행 종료는 별개이며 실제 근거·남은 live/blocked 문맥을 기록합니다.
9. 측정/승인 대기 중에는 다른 성장 후보의 연구·기획·자사 콘텐츠/소재 준비를 진행합니다. 모든 안전한 후보와 새 조사 근거가 막혔을 때만 팀별 blocker·재검토 조건을 남기고 변경 없이 종료합니다.

## PM 감독과 Task/Dispatch 계약

PM은 선택한 한 성장 과제를 15분 안에 검증·인계 가능한 작은 Task로 나눕니다. 매 Task에 다음을 넣습니다.

```text
Target: 대상 파일·서비스·환경과 선택한 .omp/agents/<역할>.md를 먼저 읽기
Change: 이번 Task의 구체적 산출물
Constraints: 불변 조건·비용/외부 활동 금지·운영 토큰/서버 start·finish 금지
Ownership: 역할 owns 안의 정확한 수정 경로·공유 계약 소유자·수정 금지 경로
Prerequisites: 이미 확보한 계약/디자인/연구 근거와 실제 선행 Task
Observable acceptance: 실행할 로컬 시나리오·기대 출력/상태·제출할 근거
```

PM은 Orca orchestration 스킬의 설치된 CLI 계약을 읽고 하나의 Orca Run에 Task와 유일한 활성 Dispatch를 기록합니다. 서버 `agent_run`과 Orca Run은 다른 식별자입니다. 보통 `orca orchestration worker-start --spec "<위 계약>" --worktree <정확한 선택자> --agent omp --model openai-codex/gpt-6.1-sol --json`으로 실행하며 Task ID·Dispatch ID·실제 역할·terminal/worktree·모델을 `refs`/연결 work item에 남깁니다. 필요한 작업에만 실제 선행 의존성을 둡니다.

- 워커는 주입된 Task/Dispatch 권한과 heartbeat 간격을 따릅니다. 질문은 `orca orchestration ask`로 PM에게 전달하고 같은 message ID로 재개합니다. 사람 승인 경계는 PM이 중앙 조정·기존 사람 요청으로 올리며 워커가 대신 결정하지 않습니다.
- `worker_done`은 정확히 한 번, Task ID와 Dispatch ID 둘 다, `succeeded` 또는 `failed` outcome, 실제 행동·발견·남은 일의 3문장 요약과 변경 파일/근거를 보냅니다. 실패를 요약에만 숨기지 않습니다. 완료 후 워커는 idle로 멈춥니다.
- PM은 `check`의 Delivery를 읽어 모든 질문/결과를 처리하고 활성 Dispatch와 근거를 대조한 뒤 ack합니다. 유효한 `worker_done`이 Task/Dispatch를 자동 settlement하므로 별도 완료 상태를 덮어쓰지 않습니다. accepted settlement마다 즉시 같은 검증된 터미널을 새 Dispatch로 재사용하거나, 사용자 요청 보존을 `worker-retain`으로 기록하거나, `worker-release`합니다. 재사용은 receipt로 확인한 같은 Sol 세션만 가능하며 역할 파일을 다시 지정합니다.
- 무응답·timeout·전송 접수는 실패/종료 증거가 아닙니다. `live`/`unverifiable`/`exited`를 구분하고 blind duplicate dispatch·재시도를 하지 않습니다. 명시적 종료 증거가 있어야 실패 복구 계약에 따라 stop/abandon/retry할 수 있으며, release는 accepted settlement 뒤만 가능합니다. 불확실한 release는 receipt의 복구 절차를 따르고 `terminal close`로 대신하지 않습니다.
- 15분은 무리한 완료 약속이 아니라 착수 범위의 상한입니다. 후반에는 새 Task를 열지 않고 검증·질문 해결·결과 인계를 우선합니다. 시간에 맞추려고 live/검증 불가 워커를 삭제하거나 실행 중 작업을 완료로 표시하지 않습니다. 끝나지 않은 Dispatch의 ID·liveness·소유 경로·변경 보존 위치·blocker·재확인 조건을 다음 실행에 남기고, 그 소유권이 해소되기 전 중복 편집을 금지합니다.

감독 워커의 `worker-release`는 settlement 후 자원 정리이며, 이전에 완료된 일반 자동화 worktree 삭제와 다릅니다. 일반 정리는 [실행 프롬프트](ai-operator-prompt.md)의 provenance·완료 후 20분·커밋 보존·clean tree·idle/종료·로컬 인스턴스·pinned/자식/미병합 보존 조건을 모두 유지합니다. release 성공만으로 worktree/커밋 삭제를 허용하지 않습니다.

조사는 필요한 선행 조건이지 이미 조사된 구현의 대체물이 아닙니다. 기존 연구·PRD·설계가 충분하면 바로 해당 미완료 수용 기준의 구현/검증 Task를 맡깁니다. 비용·외부 계정·법률 위험은 실행하지 않고 다음 행동에 승인 조건으로 남깁니다.

## 팀별 연구와 보고

매 실행 Product, Research, Growth, Events, Web, API, SRE, QA를 구분해 보고합니다. 각 팀은 유지보수 목록이 아니라 실사용자 증가에 기여하는 과제를 제안합니다. SRE·QA는 선택한 성장 과제의 출시 가능성과 차단 위험을 보고하며 근거 없이 인프라/보안 개선을 주목표로 바꾸지 않습니다.

팀별 보고에는 다음을 모두 남깁니다.

1. 조사일·출처 URL/코드/운영 지표·확인한 사실·추론·정보 공백.
2. 대상 사용자·병목·성장 가설과 후보 두 개 이상. 기존 보고 재사용이면 마지막 확인일과 변화 없음/변화 내용을 명시합니다.
3. 추천 수행 과제와 보류 대안의 이유·연결 work item. 조사 실패는 실패와 시도한 출처를 기록하고 결과를 꾸미지 않습니다.
4. 이번 실행의 실제 행동과 상태(미착수/설계/구현/출시/측정 대기/승인 대기). 출시나 성장 성과를 미리 주장하지 않습니다.
5. 주 지표·측정 가능한 분모/없는 분모·안전 지표·배포 기준 시각·측정일·중단/롤백 조건.
6. 비용·외부 게시/발송·계정·보상·법률/개인정보 승인 여부와 다음 구체적 행동.

매 실행 최소 한 팀을 새 근거로 심층 조사하고, 나머지 팀은 최신 보고를 검토합니다. 가장 오래 조사한 팀부터 순환하여 정상 실행 8회 안에 모든 팀을 새 근거로 갱신합니다. 실행 실패/중복 건너뜀은 조사 회차로 세지 않습니다. 선택할 성장 과제의 근거는 해당 실행에서 다시 확인합니다. 출처를 읽지 않은 팀을 새 조사 완료로 표시하지 않습니다.

팀별 상세 보고는 연결 work item 또는 `docs/product/research/`의 같은 보고를 갱신하고, `agent_runs.actions`에는 `팀명: 근거·추천/보류·행동`, `nextSteps`에는 `팀명: 다음 행동·측정일·blocker`를 남깁니다. 조사마다 새 문서·티켓을 쌓지 않고 기존 자료를 재사용하며, 상태 원본은 work item의 `상태` 줄입니다.

팀별 상태는 `조사/설계`, `구현 중`, `로컬 검증`, `main 반영`, `운영 실행`, `효과 측정`으로 구분합니다. 실행 근거가 없는 팀은 `새 실행 없음`이며 마지막 보고 확인일을 남깁니다. 실제 역할·Task/Dispatch·수행 명령·관측 결과를 연결하고 다른 팀의 시험/문서/배포 계획을 해당 팀의 출시·성장 성과로 바꾸지 않습니다.

신규 기능·자사 마케팅 자산·이벤트 후보를 함께 비교합니다. 도달할 타깃·사용자 가치·관측 가능한 영향·불확실성·작업 범위·승인/비용·되돌림을 적고 한 과제를 선택합니다. 유입이 적으면 기능 늘리기만 반복하지 않으며, 승인 대기 외부 마케팅과 별개로 자사 가이드·예시·소재를 제작합니다. 숫자 근거 없는 전환율/성장률 점수는 만들지 않습니다.

초기 PM은 [그로스 조사 보고](../product/research/crelink-growth-team-research.md)와 기존 `0168` 시작 키트·`0169` 챌린지의 미완료 수용 기준을 인계받습니다. 이는 두 과제가 출시됐다는 뜻이 아닙니다. 상태 원본과 실제 근거를 확인해 구현/검증 가능한 다음 행동을 선택하고 이후 추천 변경의 근거·보류 이유를 같은 자료에 갱신합니다.

## 기간별 계획과 가상 사용자 검증

매 실행 과제 선택은 [팀별 성장 로드맵](crelink-growth-roadmap.md)의 8팀·4기간·P0/P1/P2와 연결합니다. P0의 발동 조건, 선택한 기간/우선순위, 산출물·완료 조건·측정·승인·다음 행동을 팀별 보고에 남깁니다. 기간은 착수 이후 목표 구간이지 동시 착수/자동 출시 약속이 아닙니다.

실제 구현 검증은 [가상 사용자 테스트](../development/user-simulation.md)의 정상·edge·모의 시나리오를 localhost 실제 API/DB에서 실행합니다. 테스트 계정은 기본 지표 제외이며, 지표 포함 대조군도 로컬 합성 계정입니다. 운영 계정/실사용자·운영 DB를 시험 대상으로 쓰거나 가상 완료/선호를 성장·수요 증거로 보고하지 않습니다. 운영의 기존 시험 계정 분류를 AI가 우회해서 바꾸지 않습니다.
