# 제품 탐색과 PRD

새 서비스나 방향을 바꿀 수 있는 큰 기능은 PRD를 확정하기 전에 **탐색 조사**를 마칩니다. 유사 서비스에서 배울 점과 피할 점, 서비스를 만들 때 쓸 라이브러리·오픈소스·SaaS 후보를 먼저 확인해 두면, 구현 중에 "이미 있는 해법"이나 "쓸 수 없는 라이선스"를 발견해 방향을 바꾸는 일을 줄일 수 있습니다. 조사가 방향 변경을 없애 주지는 않으므로, 조사 결과는 결정이 아니라 근거로 남기고 결정은 사용자가 합니다.

에이전트가 따르는 조사 절차와 평가 기준은 [product-discovery 스킬](../../.omp/skills/product-discovery/SKILL.md)에 있습니다. 상태·전이 규칙은 [ALM 운영 기준](../alm/workflow.md), work item 형식은 [작업 관리](../work/README.md)를 따릅니다.

## 흐름

```text
문제·대상 사용자 정리 ─┬─ 유사 서비스 벤치마킹(product) ─┐
                      └─ 기술 조사(orchestrator + 영역 agent) ┴─ PRD 초안(product) → 사용자 확정 → 디자인 → 기술 설계·티켓 분해
```

1. **문제 정리**: 누구의 어떤 문제를 푸는지, 지금은 어떻게 해결하는지, 성공을 어떻게 알아볼지 한 쪽으로 적습니다. PRD의 `문제`·`대상 사용자` 절 초안이 됩니다.
2. **유사 서비스 벤치마킹**: `product`가 직접 경쟁·간접 경쟁·대체 수단을 조사해 [벤치마킹 문서](research/TEMPLATE.md)로 남깁니다.
3. **기술 조사**: `orchestrator`가 PRD 초안의 핵심 기능을 구현할 라이브러리·오픈소스·SaaS 후보를 조사해 [기술 조사 문서](../references/TEMPLATE.md)로 남기고, 스택 적합성은 해당 영역 agent(`api`, `web`, `app`, `infra`)에 확인받습니다.
4. **PRD 초안**: 조사 결과를 근거로 [PRD 템플릿](TEMPLATE.md)을 채웁니다. 요구마다 `사용자 확정`·`AI 제안`·`미정`을 표시합니다.
5. **확정**: 사용자가 범위·우선순위·성공 지표와 기술 후보를 정합니다. 장기 기술 선택은 범위에 맞는 ADR을 `제안` 상태로 쓰고, 사용자 확인 후 `승인`으로 바꿉니다.
6. **다음 단계**: 확정된 PRD로 디자인 프로토타입을 만들고(`designer`), 여러 역할이 구현하는 기능은 [기술 설계와 티켓 분해](../specs/README.md)(`orchestrator`)를 거쳐 구현 티켓을 만듭니다. 한 역할 안에서 끝나는 작은 기능은 티켓으로 바로 나눕니다.

탐색 단계는 work item으로 추적합니다. 예: 에픽 `서비스 MVP` 아래 `product` 티켓 "유사 서비스 벤치마킹과 PRD 초안"(종류 `제품 결정`), `orchestrator` 티켓 "핵심 기능 기술 조사"(종류 `제품 결정`), 이 둘을 `선행`으로 둔 `designer` 디자인 티켓과 `orchestrator` 기술 설계 티켓. 구현 티켓은 설계 승인 후 설계 문서의 분해안으로 만듭니다.

## 문서 위치

| 문서 | 위치 | 담당 |
| --- | --- | --- |
| PRD | `docs/product/<서비스 또는 기능>.md` ([템플릿](TEMPLATE.md)) | `product` 초안, 사용자 확정 |
| 유사 서비스 벤치마킹 | `docs/product/research/<주제>.md` ([템플릿](research/TEMPLATE.md)) | `product` |
| 라이브러리·오픈소스·SaaS 기술 조사 | `docs/references/<주제>.md` ([템플릿](../references/TEMPLATE.md)) | `orchestrator`(영역 agent 확인) |
| 기술 선택 결정 | 범위에 맞는 `adr/` | 조사 담당이 `제안`으로 작성, 사용자 확인 후 `승인` |

PRD와 벤치마킹 문서는 이 폴더의 색인([문서 색인](../README.md))에 링크합니다. 조사 문서(`docs/references/`, `docs/product/research/`)는 `pnpm docs:check`가 `확인일` 날짜 형식과 출처 URL이 하나 이상 있는지 검사합니다.

이 위치를 정하기 전부터 저장소에 있던 조사 문서(예: `docs/references/`의 벤치마킹)나 다른 이름의 PRD(예: `docs/product/requirements.md`)는 옮기거나 이름을 바꾸지 않고 그대로 두며, 위 표에 행을 추가하거나 [문서 색인](../README.md)에서 연결합니다. 새 문서만 위 위치를 따릅니다.

## 조사 품질 기준

- **출처와 확인일**: 모든 사실에 출처를 달고, 문서 머리에 `- 확인일: YYYY-MM-DD`를 둡니다. 날짜 뒤에 공백과 메모를 붙일 수 있습니다(예: `- 확인일: 2026-10-01 (가격은 이날 기준)`). 출처는 `[이름](URL)` 링크나 맨 URL로 적습니다. 가격·라이선스·유지보수 상태처럼 바뀌는 정보는 결정 직전에 다시 확인합니다.
- **사실·추론·제안 구분**: 출처로 확인한 사실, 근거에서 끌어낸 추론, 저장소에 주는 제안을 섞지 않습니다. 제안은 `AI 제안`으로 표시합니다.
- **범위**: 벤치마킹은 직접 경쟁 3개 이상과 간접 경쟁·대체 수단을 포함합니다. 기술 조사는 핵심 기능마다 후보 2개 이상과 "직접 만들기"를 비교합니다. 후보가 하나뿐이면 그 이유를 적습니다.
- **결론**: 각 문서는 "따라 할 것 / 피할 것 / 미정" 또는 "추천 후보와 탈락 이유"로 끝냅니다. 결론이 PRD 요구나 ADR 어디에 반영됐는지 링크합니다.
- **시간 제한**: 조사는 결정을 위한 것입니다. 티켓에 조사 질문과 끝낼 조건을 적고, 답하지 못한 질문은 `미정`으로 남겨 사용자 결정으로 넘깁니다.
