# 기술 설계와 티켓 분해

확정된 PRD와 디자인 인계를 받아, 무엇을 어떤 구성요소가 어떤 계약으로 만들지 정하고 역할별 티켓으로 나누는 단계입니다. 기능을 구현 티켓으로 바로 쪼개면 계약·데이터·화면 상태의 빈틈이 구현 중에 드러나 여러 역할이 동시에 되돌아가야 합니다. 설계 문서는 그 빈틈을 티켓이 `준비`로 올라가기 전에 드러내기 위한 것입니다.

에이전트가 따르는 작성·분해 절차는 [technical-design 스킬](../../.omp/skills/technical-design/SKILL.md)에 있습니다. 앞 단계는 [제품 탐색과 PRD](../product/README.md)와 [OpenDesign 사용 기준](../../design/docs/opendesign.md), 상태 규칙은 [ALM 운영 기준](../alm/workflow.md)을 따릅니다.

## 언제 쓰나

| 변경 | 설계 문서 |
| --- | --- |
| 둘 이상의 역할이 바뀌는 기능, 새 API 계약·데이터 모델, 인증·권한·개인정보·결제가 걸린 변경 | 필요 |
| 한 역할 안에서 끝나고 계약·데이터가 바뀌지 않는 변경(문구, 화면 배치, 내부 리팩터링) | 티켓만으로 충분 |

## 흐름

```text
PRD 확정 ─▶ 디자인 프로토타입 ⇄ 디자인 기술 검토 ─▶ 디자인 인계
                                                   │
                       기술 조사·ADR(제안) ─────────┤
                                                   ▼
                     설계 초안 ─▶ 검토(api·designer·product) ─▶ 사용자 승인 ─▶ 티켓 분해 ─▶ 실행
```

1. **디자인 기술 검토**: 디자이너가 프로토타입을 사용자에게 승인받기 전에 `orchestrator`가 구현 가능성을 봅니다. 화면이 요구하는 데이터가 얻을 수 있는 것인지, 플랫폼(웹·Expo) 제약에 걸리는 상호작용이 있는지, 상태(로딩·빈 상태·오류·권한 없음)가 빠지지 않았는지 확인하고, 걸리는 점은 설계 문서 초안의 `디자인 검토 의견`에 남겨 디자이너에게 돌려보냅니다. 디자이너는 반영 결과를 `handoff.md`의 기술 검토 항목에 링크합니다.
2. **설계 초안**: `orchestrator`가 [템플릿](TEMPLATE.md)으로 `docs/specs/<에픽 slug>.md`를 씁니다. 요구 대응표, 데이터·API 계약 초안, 화면 상태와 API의 대응, 권한·비기능, 위험과 스파이크, 티켓 분해안, 검증 계획을 담습니다.
3. **검토**: 해당 역할이 자기 부분을 확인합니다. 의견은 설계 문서 `검토 기록`에 남기고, 바뀐 결정은 본문에 반영합니다.
4. **승인**: 사용자가 설계를 승인하면 `상태: 승인`으로 바꿉니다. 장기 기술 선택은 같은 때 ADR을 `승인`으로 바꿉니다.
5. **티켓 분해**: 승인된 분해안대로 에픽·티켓을 만들고 `pnpm work:check`로 확인합니다. 아래 [분해 규칙](#분해-규칙)을 따릅니다.

## 역할

| 역할 | 맡는 일 |
| --- | --- |
| `orchestrator` | 디자인 기술 검토, 설계 문서 작성·갱신, 티켓 분해, 에픽 통합 검증 |
| `api` | API 계약(경로·메서드·요청·응답·오류·권한)과 데이터 모델 검토. 승인 후 계약 티켓에서 `packages/shared` 반영 |
| `web`·`app` | 화면 상태와 API 대응, 플랫폼 제약 검토. 각자 구현 티켓 |
| `infra` | 새 인프라 의존(저장소, 큐, 외부 서비스 연결)이 있을 때 검토 |
| `designer` | 화면 상태·상호작용이 설계와 맞는지 확인, 디자인 검토 의견 반영 |
| `product` | PRD 요구가 빠짐없이 대응되는지, 범위가 PRD와 같은지 확인 |
| 사용자 | 설계 승인, 미정 사항 결정 |

## 분해 규칙

- **한 티켓은 한 역할의 소유 경로만** 바꿉니다(`pnpm work:scope`). 여러 영역에 걸친 연결(루트 설정, CI, 통합)은 `orchestrator` 티켓입니다.
- **계약이 먼저입니다.** 새 API가 있으면 `api` 계약 티켓(`packages/shared` DTO·오류 코드 확정)을 만들고, 웹·앱·API 구현 티켓의 `선행`에 겁니다. 계약이 통합되면 구현 티켓은 병렬로 진행합니다. 웹·앱은 계약 기반 mock으로 먼저 구현할 수 있습니다([영역별 병렬 개발](../development/parallel-work.md#계약과-병렬화-경계)).
- **불확실성은 스파이크로** 분리합니다. 라이브러리 동작, 성능, 플랫폼 제약처럼 답을 모르는 질문은 짧은 조사 티켓으로 만들고 결과로 설계를 갱신한 뒤 해당 구현 티켓을 `준비`로 올립니다.
- **티켓 크기**는 PR 하나, 에이전트 실행 한 번(기본 제한 60분, `WORKFLOW.md`)에 끝나고 혼자 검증할 수 있는 정도입니다. 더 크면 하위 티켓으로 나눕니다.
- **수용 기준은 관찰 가능하게** 씁니다. 각 기준에 확인 방법(실행할 명령, 확인할 화면 상태, API 응답)을 붙이고, 담당 PRD 요구 번호(R1…)와 설계 문서 절을 `연결`에 적습니다.
- **통합 티켓**을 에픽마다 하나 둡니다(`orchestrator`). mock을 실제 API로 바꾼 경로에서 설계의 검증 계획(E2E 시나리오)을 실행하고 에픽 통합 수용 기준을 확인합니다. `pnpm smoke`는 화면과 무관한 불변 조건만 보므로 기능 시나리오를 넣지 않습니다.
- **선행은 진짜 의존만** 겁니다. 순서를 위해 거는 선행은 병렬 실행을 막습니다.

## 문서 위치와 상태

- 설계 문서: `docs/specs/<에픽 slug>.md`. 에픽 work item의 `연결`에 링크하고, 에픽 파일에는 설계 내용을 복사하지 않습니다.
- 상태: 문서 머리의 `- 상태: 초안 | 검토 | 승인 | 대체됨`. 승인 후 바뀐 결정은 `변경 기록` 절에 날짜와 이유를 남기고 영향받는 티켓의 `진행 기록`에도 적습니다. 범위가 크게 바뀌면 새 설계 문서를 만들고 이전 문서를 `대체됨`으로 표시합니다.
- 설계 문서는 구현의 계획이며 현재 구현 사실의 원본이 아닙니다. 구현이 끝난 계약·데이터 구조의 기준은 코드(`packages/shared`, migration)입니다.
