# ALM 운영 기준

이 문서는 crelink의 애플리케이션 수명 주기 관리(ALM) 기준입니다. ALM은 특정 도구나 폴더 구조가 아니라 제품 요구를 구상하고, 변경하고, 검증·배포·운영하며, 필요하면 안전하게 종료하기 위한 연결된 작업 방식입니다.

## 기록의 소유권

같은 사실을 여러 곳에 복사하지 않습니다. 도구는 교체될 수 있지만 저장소의 이 기준과 버전 이력은 유지합니다.

| 정보 | 기준 원본 |
| --- | --- |
| 제품 목적·사용자 가치·확정/제안/미정 요구사항 | 제품 요구 문서와 그 요구사항을 뒷받침하는 디자인 근거. 현재는 제품 요구 문서가 없고 컨셉과 상태만 루트 [README](../../README.md)에 있음 |
| 개별 변경·결함·운영 후속 작업과 진행 상태 | 저장소의 work item 파일(에픽은 `docs/work/epics/`, 티켓은 역할별 폴더 `docs/work/<역할>/`). 형식과 진행 방법은 [작업 관리](../work/README.md)에서 관리 |
| 설계 선택과 장기 트레이드오프 | 범위에 맞는 ADR. 구현 상태나 작업 목록의 대체물이 아님 |
| 실제 구현·환경 설정 | 소스 코드, 설정, migration, 버전 관리 이력 |
| 실제 검증 근거 | 테스트·CI 결과 또는 구체적인 수동 검증 기록. 해당 work item이나 변경과 연결 |
| 모든 변경 이력(공개 여부 무관) | 영역별 `CHANGELOGS.md`와 루트 [CHANGELOGS](../../CHANGELOGS.md). 내부 참고용 |
| 사용자에게 공개된 제품 릴리스 | 루트 [RELEASES](../../RELEASES.md)와 해당 Git tag |
| 환경별 배포·운영 결과 | 해당 운영 work item과 배포 플랫폼. 정확한 배포 시각·환경·결과·복구 근거를 기록 |

제품 요구 문서를 만들면 각 요구에 `사용자 확정`, `AI 제안`, `미정` 상태를 표시합니다. 미정·제안 내용을 확정 요구사항으로 취급하지 않습니다. 구현용 work item은 관련 요구사항을 링크하고, 해당 변경의 관찰 가능한 수용 기준만 기록합니다. 제품 요구 문서 전체 내용을 work item에 복사하지 않습니다.

## Work item

기능·결함·유지보수·운영 후속 등 의미 있는 변경은 work item으로 추적합니다. 이름·URL·프로젝트 ID 같은 작업 관리 도구의 식별자는 도구 전용으로 취급합니다. 저장소 문서·ADR·커밋에 도구 고유 번호를 필수 기준으로 박지 않습니다.

복잡도에 맞춰 다음 필드를 기록합니다.

- **종류·제목:** 기능, 결함, 유지보수, 운영 중 무엇을 다루는지.
- **목적:** 어떤 사용자 문제·위험·품질 비용을 줄이는지.
- **결과와 수용 기준:** 변경이 관찰 가능하게 완료됐다고 판단할 조건. 중요 동작의 상태 전이·경계·오류·권한을 명시합니다.
- **범위:** 포함 범위와 필요하면 명시적 제외 범위.
- **우선순위:** 지금 진행할 이유와 다른 작업 대비 순서. 숫자 점수화는 요구하지 않습니다.
- **위험·복구:** 데이터·권한·secret·결제·외부 서비스·비가역 동작에 영향이 있으면 영향과 복구·롤백 방법.
- **연결:** 제품 요구·디자인·ADR·관련 코드 변경·검증·실제 배포/운영 기록.

work item은 사용자에게 보이는 결과인 **에픽**, 한 역할의 작업인 **티켓**, 티켓의 세부 작업인 **하위 티켓** 3단계로 나눌 수 있습니다. 사용자 관점의 수용 기준과 영역 간 통합 검증은 에픽에, 영역별 결과와 계약은 티켓에 둡니다. 결함·유지보수·운영·제품 결정은 상위 없는 독립 티켓으로 둘 수 있습니다. 상위·선행 관계와 역할은 각 work item의 필드로 기록합니다. 저장 위치는 역할을 구분할 뿐 계층을 나타내지 않습니다.

단순 오탈자나 위험이 낮은 작은 변경은 별도 work item을 강제하지 않습니다. 여러 영역에 영향이 있거나 요구·수용 기준·검증을 나중에 추적해야 하는 일, 운영·데이터·보안 위험이 있는 변경은 work item을 만듭니다.

## 상태와 전이

| 상태 | 의미와 진입 기준 |
| --- | --- |
| **분류 대기** | 새 제안·피드백. 중복·범위·가치·위험을 확인하기 전 |
| **준비** | 목적·수용 기준·필요한 범위가 이해 가능하고 우선순위가 정해져 착수할 수 있음 |
| **진행** | 구현·조사·설계가 실제로 진행 중 |
| **검증** | 구현을 마쳤고, 수용 기준과 필요한 테스트·검토를 확인 중 |
| **완료** | 수용 기준을 충족하고 변경이 저장소에 통합됨. 필요한 문서·운영 안내도 갱신됨 |
| **보류/종료** | 지금 진행하지 않거나 더는 필요하지 않음. 사유와 재개 조건 또는 대체 work item을 남김 |

- **준비 전 착수하지 않습니다.** 단, 장애 완화처럼 즉시 대응이 필요한 경우 먼저 안전한 조치를 하고 사후에 목적·영향·검증을 기록합니다.
- 구현이 끝났다고 검증을 생략하지 않습니다. 수용 기준에서 요구하는 실행 경로를 확인합니다.
- `완료`는 구현·검증의 완료이지 운영 배포의 주장이 아닙니다. 배포된 경우에만 별도로 환경·버전/커밋·시각·결과를 기록합니다.
- 요구가 바뀌면 기존 수용 기준을 조용히 덮지 않습니다. 범위 변경과 결정 근거를 work item 또는 ADR에 기록합니다.
- 보류·종료 항목은 삭제하지 않고 상태와 이유를 보존합니다. 대체된 설계 결정은 ADR에 `대체됨`으로 표시합니다.

## 변경부터 운영까지

1. **요구·피드백을 받습니다.** 사용자 문제, 제품 목표, 장애 신호를 기록합니다. 제품 범위 변경은 제품 요구 문서·디자인과 대조합니다.
2. **분류하고 준비합니다.** 가치·범위·수용 기준·우선순위·위험을 구분합니다. 새 서비스나 방향을 바꿀 수 있는 큰 기능은 준비 전에 유사 서비스 벤치마킹과 라이브러리·오픈소스·SaaS 기술 조사를 마치고 PRD를 확정합니다([제품 탐색과 PRD](../product/README.md)). 여러 역할이 구현하거나 새 API 계약·데이터 모델이 필요한 기능은 구현 티켓을 `준비`로 올리기 전에 기술 설계를 승인받고 그 분해안으로 티켓을 만듭니다([기술 설계와 티켓 분해](../specs/README.md)). 장기적인 기술 선택에 여러 대안과 트레이드오프가 있으면 구현 전에 해당 범위 ADR을 작성합니다.
3. **작게 변경합니다.** 기존 모듈 경계와 SSoT를 따릅니다. 사용자에게 보이는 동작, 데이터, 보안, 비용, 다른 앱/API와 계약에 미치는 영향을 살핍니다.
4. **검증합니다.** 수용 기준을 실제 경로에서 확인하고 결과를 기록합니다. 테스트 성공만으로 화면·CLI·네트워크·DB·배포 경로가 동작한다고 단정하지 않습니다. 운영·데이터·권한 변경에는 필요한 복구 검증을 추가합니다. 저장소에서 실행하는 명령과 범위는 [검증 루프](../development/verification.md)가 기준입니다.
5. **통합·기록합니다.** 커밋/PR과 work item을 연결하고 관련 코드·설정·문서를 함께 갱신합니다. 공개·적용 여부와 관계없이 변경한 영역의 `CHANGELOGS.md`에 기록합니다.
6. **필요한 환경에 배포합니다.** 실제 배포를 수행한 경우 대상 환경, 버전/커밋, 시각, 결과와 필요한 복구 정보를 운영 work item이나 플랫폼에 남깁니다. 개발 환경 검증은 운영 배포가 아닙니다.
7. **릴리스를 공개·기록합니다.** 사용자에게 공개한 릴리스는 루트 `RELEASES.md`에 버전·날짜·Git tag·대상과 사용자 관점의 변경 내용을 기록하고, 포함된 `CHANGELOGS.md` 항목에 해당 릴리스 버전을 표시합니다. GitHub Release를 쓰면 같은 tag의 `RELEASES.md` 항목을 설명의 원본으로 합니다.
8. **운영에서 배우고 종료합니다.** 사용자 피드백·장애·성능·비용 신호를 새 work item으로 연결합니다. 서비스나 기능을 끝낼 때 사용자 영향, 데이터 보존·이전·삭제, 통신, 자원·계정·secret 회수를 다룹니다.

## 릴리스 단위와 기록

`CHANGELOGS.md`는 내부 참고용 전체 변경 기록이고, `RELEASES.md`는 공개용 릴리스 노트입니다. 둘의 역할을 섞지 않습니다.

- 영역별 `CHANGELOGS.md`(`infra/`, `apps/api/`, `apps/web/`, `apps/app/`)는 해당 영역의 모든 변경을 공개·적용 여부와 관계없이 기록합니다. 전용 로그가 없는 영역(`design/`, `packages/`, `docs/`, `.github/`, 루트 설정·정책)과 여러 영역에 걸친 작업의 요약은 루트 `CHANGELOGS.md`에 둡니다.
- 변경 기록 항목은 날짜별 제목(최신순) 아래에 변경 내용과 근거(커밋, work item, 관련 경로)를 적습니다. 공개 릴리스에 포함되면 해당 `RELEASES.md` 버전을 표시합니다.
- `RELEASES.md`는 사용자에게 실제로 공개한 릴리스만 기록합니다. 각 항목은 버전, 날짜, Git tag, 대상(웹·앱·API 등)과 사용자 관점의 변경 내용을 담고, 내부 구현 세부·미공개 계획·비밀값은 넣지 않습니다.
- 환경별 배포 시각·결과·복구 정보는 운영 work item이나 배포 플랫폼에 남깁니다.

현재 세부 배포 대상과 미구현 범위는 [배포 대상 아키텍처](../architecture/deployment-target.md)를 기준으로 확인합니다.

## 위험에 비례한 검증

영향이 작고 되돌리기 쉬운 변경에는 가벼운 확인을 적용합니다. 다음 변경은 추가 검토와 구체적인 복구 방법이 필요합니다.

- 사용자 데이터, schema/migration의 변경
- 인증·권한·개인정보·secret 또는 외부 제공자의 자격 증명
- 네트워크 노출, 운영 배포, 과금 자원, 외부 서비스 생성·삭제
- 데이터 삭제, 키 회전, 대량 변경 등 되돌리기 어려운 작업

운영 자원 생성·삭제·배포나 사용자 데이터 변경은 대상과 영향을 명확히 확인합니다. 자동화가 있다는 이유만으로 승인·접근 제한을 생략하지 않습니다.

## 작업 관리 도구 교체

작업 관리 도구는 현재 서비스의 형식과 무관하게 다음 필드를 내보내고 다시 가져올 수 있어야 합니다: 제목·단계·역할·상위·선행·종류·목적·범위·수용 기준·우선순위·위험·상태·연결·종료/보류 사유.

도구를 바꿀 때는 진행 중뿐 아니라 완료·보류 기록도 필요한 보존 정책에 따라 내보냅니다. 수용 기준·댓글에만 존재하는 결정 근거·상태·링크를 새 도구로 매핑하고, 원래 도구의 ID/URL을 이전 출처로 보존하며 레코드 수와 핵심 연결을 대조한 뒤 전환합니다. Git 커밋·코드·ADR·제품 문서는 이전 도구의 가용성에 의존하지 않게 유지합니다. 현재는 [ADR 0002](../adr/0002-work-items-in-repository.md)에 따라 work item을 저장소 문서([작업 관리](../work/README.md))로 관리하며 GitHub Issues를 쓰지 않습니다.

## 범위와 무절차 기준

이 방식은 1인 개발에 맞는 최소 기록 기준입니다. 모든 커밋에 work item을 강제하지 않고, 승인자·회의·개별 문서 복제를 요구하지 않습니다. 정량 제품 KPI는 목표가 정해지고 실제 측정이 가능해진 뒤 도입합니다.
