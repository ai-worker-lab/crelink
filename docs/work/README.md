# 작업 관리 (work item)

crelink의 work item은 이 폴더의 Markdown 파일로 관리합니다. GitHub Issues는 사용하지 않습니다([ADR 0002](../adr/0002-work-items-in-repository.md)). work item을 에픽·티켓·하위 티켓 3단계로 나누는 결정은 [ADR 0003](../adr/0003-work-item-hierarchy.md)입니다. 필드·상태·전이의 도구 중립 기준은 [ALM 운영 기준](../alm/workflow.md)이 원본이며, 이 문서는 그 기준을 저장소 파일로 구현하는 규칙을 정합니다.

## 명령

```sh
pnpm work                             # 에픽 → 티켓 → 하위 티켓 트리와 진행률
pnpm work:check                       # 아래 규칙 검사. 위반이 있으면 실패
pnpm work:next [--all] [--json]       # 착수 가능한 work item. --all은 제외 사유까지
pnpm work:place [NNNN ...] [--dry-run] # 단계·역할에 맞는 폴더로 옮기고 그 파일의 상대 링크를 고침
pnpm work:scope [NNNN] [--base <ref>] # 티켓 역할의 소유 경로 밖 변경 검사
pnpm work:run [--once] [--dry-run]   # 착수 가능한 work item마다 worktree와 코딩 에이전트 실행
pnpm work:run --print-prompt [NNNN]  # 에이전트를 실행하지 않고 프롬프트만 출력
```

`work`, `work:check`, `work:next`, `work:place`는 [scripts/work.mjs](../../scripts/work.mjs), `work:scope`는 [scripts/work-scope.mjs](../../scripts/work-scope.mjs)(소유 경로 원본은 `.omp/agents/*.md`의 `owns`, [영역별 병렬 개발](../development/parallel-work.md#역할과-에이전트별-소유-경계)), `work:run`은 [작업 실행기](../development/agent-runner.md)가 실행합니다. work item을 추가·수정하면 커밋 전에 `pnpm work:check`를 실행합니다.

`work:scope`는 기준 이후 티켓 브랜치에서 커밋한 변경과 작업 트리의 변경을 셉니다. `--base`를 생략하면 [WORKFLOW.md](../../WORKFLOW.md)의 `workspace.base`(기본 `main`)와 `origin/<같은 이름>` 중 HEAD와의 머지 베이스가 더 최근인 쪽에서 비교하므로, 로컬 기준 브랜치가 `origin`보다 앞서거나 뒤처져도 티켓 브랜치의 커밋만 셉니다. 둘 다 없으면 `git fetch` 또는 `--base`를 안내하고 실패합니다. `--base <ref>`를 주면 그 ref와 HEAD의 머지 베이스에서 비교합니다(CI는 PR의 `--base origin/<기준 브랜치>`). 출력에 쓰인 기준이 표시됩니다.

## 단계

| 단계 | 의미 | 수용 기준 | 역할 | 상위 |
| --- | --- | --- | --- | --- |
| `에픽` | 사용자에게 보이는 결과 하나. 제품 요구와 연결 | 사용자 관점의 끝까지의 동작과 영역 간 통합 검증 | 없음. 통합 검증은 `orchestrator`가 맡음 | 없음 |
| `티켓` | 한 역할이 맡는 작업. 에픽을 역할별로 나눈 단위이거나 독립 작업 | 그 영역의 결과와 계약(API 요청·응답, 화면 상태 등) | 필수 | `에픽` 또는 없음 |
| `하위 티켓` | 티켓의 세부 작업 | 구체적인 구현·검증 단위 | 필수. 상위 티켓과 같은 역할 | `티켓` 필수 |

- 이 저장소에서 "티켓"은 work item의 단계 이름이며 GitHub Issue를 뜻하지 않습니다. 세 단계를 함께 부를 때는 work item이라고 합니다.
- 결함·유지보수·운영·제품 결정처럼 사용자 가치 단위가 아닌 작업은 상위 없는 독립 티켓으로 둡니다. 묶기 위한 에픽을 만들지 않습니다.
- 하위 티켓은 별도 상태·검증·커밋이 필요한 세부 작업만 만듭니다. 그 밖의 세부 작업은 티켓의 수용 기준 체크리스트로 둡니다.
- 역할은 `.omp/agents/*.md`의 agent `name`입니다. 역할별 소유 경로는 [영역별 병렬 개발](../development/parallel-work.md#역할과-에이전트별-소유-경계)을 따릅니다. 한 티켓은 한 역할의 소유 경로만 바꿉니다. 여러 영역을 함께 바꿔야 하는 독립 작업(루트 설정·CI·workspace 연결 등)은 `orchestrator` 티켓으로 둡니다.
- 역할 사이의 순서(예: web 티켓이 api 계약을 기다림)는 상위가 아니라 `선행`으로 표현합니다. 공유 계약(`packages/shared/`)은 api 티켓이 소유합니다.

## 파일과 필드

- 한 work item은 한 파일이고, 단계와 역할에 따라 폴더가 정해집니다([ADR 0009](../adr/0009-work-item-role-folders.md)).

```text
docs/work/
  README.md, TEMPLATE.md     규칙과 새 항목 양식(루트에는 이 둘만 둡니다)
  epics/NNNN-<slug>.md       에픽
  <역할>/NNNN-<slug>.md      티켓·하위 티켓. 폴더 이름 = `역할` 값 = .omp/agents의 agent name
```

- 번호는 폴더·단계와 관계없이 저장소 전체에서 하나인 4자리 일련번호이며 재사용하지 않습니다. 새 번호는 모든 폴더를 통틀어 다음 빈 번호입니다(`pnpm work`가 전체 번호를 보여 줍니다). 파일 이름은 `NNNN-short-title.md`, 제목 줄은 `# NNNN 제목`입니다. 새 항목은 [TEMPLATE.md](TEMPLATE.md)를 맞는 폴더에 복사해 만들고, 그 역할의 첫 항목이면 폴더를 새로 만듭니다.
- 폴더는 역할을 구분할 뿐 계층이 아닙니다. 계층은 `상위`, 순서는 `선행` 필드로 표현합니다. 하위 티켓도 상위 티켓 아래가 아니라 자기 `역할` 폴더(상위 티켓과 같은 역할이므로 같은 폴더)에 둡니다. 상위·선행을 바꿔도 파일 경로는 그대로입니다.
- 파일 머리 목록의 필드:

| 필드 | 필수 | 값 |
| --- | --- | --- |
| `단계` | 예 | `에픽`, `티켓`, `하위 티켓` |
| `역할` | 티켓·하위 티켓 | agent 이름. 에픽에는 쓰지 않음 |
| `상위` | 하위 티켓 | 상위 work item 번호 하나 |
| `선행` | 아니요 | 먼저 끝나야 하는 work item 번호. 여러 개는 쉼표로 구분 |
| `상태` | 예 | `분류 대기`, `준비`, `진행`, `검증`, `완료`, `보류/종료` |
| `종류` | 예 | `기능`, `결함`, `유지보수`, `운영`, `제품 결정` |
| `우선순위` | 예 | `P0`~`P3`. AI가 제안한 값은 사용자가 확인할 때까지 뒤에 `(AI 제안)` |
| `작성일` | 예 | `YYYY-MM-DD` |

- **관계는 한쪽에만 적습니다.** `상위`는 자식 파일에, `선행`은 뒤에 하는 쪽 파일에만 적습니다. 부모 파일에 자식 목록이나 진행률을 적지 않고 `pnpm work`로 확인합니다.
- **상태의 원본은 각 파일의 `상태` 줄 하나뿐입니다.** 다른 문서에 상태를 복사하지 않습니다.
- 우선순위: `P0` 출시·사용자 안전·진행 중인 운영 영향 차단, `P1` 다음 우선 작업, `P2` 일반 백로그, `P3` 나중에 검토.
- `완료`·`보류/종료` 파일도 삭제하지 않습니다. 사유와 재개 조건 또는 대체 항목을 남깁니다.

## 폴더 옮기기

`역할`이나 `단계`를 바꾸면 맞는 폴더가 달라지고 `pnpm work:check`가 옮길 위치와 함께 실패합니다. 필드를 고친 뒤 `pnpm work:place NNNN`으로 옮깁니다. 번호를 생략하면 폴더가 맞지 않는 모든 work item을 옮깁니다.

- 파일은 `git mv`로 옮깁니다(아직 추적하지 않는 새 파일은 이름만 바꿈). 파일 이름이 그대로라 브랜치 `work/NNNN-<slug>`도 그대로입니다.
- 저장소 Markdown 중 옮긴 파일을 가리키는 상대 링크와, 옮긴 파일 안에서 바깥을 가리키는 상대 링크를 새 위치에 맞게 고칩니다. 링크를 찾고 해석하는 규칙은 `pnpm docs:check`와 같아(`scripts/lib/markdown-links.mjs`) 코드 블록·인라인 코드 안의 경로와 외부 URL은 건드리지 않습니다.
- 링크가 아닌 옛 경로 언급(예: 변경 기록의 `` `docs/work/…md` `` 근거)은 고치지 않고 위치만 출력합니다. 지난 기록이면 그대로 두고, 현재 위치를 안내하는 문장이면 직접 고칩니다.
- `--dry-run`은 옮길 파일과 고칠 링크만 출력합니다. 옮긴 뒤 `pnpm work:check`와 `pnpm docs:check`로 확인하고 같은 커밋에 넣습니다.

## 검사 규칙

`pnpm work:check`가 다음을 확인합니다.

1. 파일 이름·제목의 번호 형식과 번호 중복(폴더가 달라도 같은 번호는 중복).
2. 필수 필드, 허용된 값, 알 수 없는 필드.
3. 단계별 상위: 하위 티켓의 상위는 티켓, 티켓의 상위는 에픽, 에픽은 상위 없음. 따라서 깊이는 최대 3단계입니다.
4. 역할: 티켓·하위 티켓에 있고 실제 agent 이름이며, 하위 티켓은 상위 티켓과 같은 역할. 에픽에는 없음.
5. `상위`·`선행`이 존재하는 번호를 가리키고, 자기 자신이나 순환을 만들지 않음.
6. `완료`인 work item의 자식이 모두 `완료` 또는 `보류/종료`.
7. 폴더 배치: 에픽은 `epics/`, 티켓·하위 티켓은 `역할`과 같은 이름의 폴더에 있음. `docs/work/` 바로 아래의 work item, 에픽도 역할도 아닌 폴더, 한 단계를 넘는 폴더는 실패이며, 오류에 옮길 위치와 `pnpm work:place NNNN`을 적습니다.

## 진행과 연결

1. 새 항목은 `상태: 분류 대기`로 만듭니다. 목적·수용 기준·범위·우선순위가 정해지면 `준비`로 바꿉니다.
2. 착수하면 `진행`, 구현을 마치면 `검증`으로 바꿉니다. 상태 변경은 해당 변경과 같은 커밋에 포함합니다.
3. `진행 기록`에 날짜별로 결정·범위 변경·검증 결과와 관련 커밋을 적습니다. 수용 기준을 조용히 고쳐 쓰지 않고 변경 이유를 남깁니다.
4. 수용 기준을 실제 경로에서 확인하고 검증 근거를 남긴 뒤에만 `완료`로 바꿉니다. 에픽은 모든 자식이 끝나고 에픽의 통합 수용 기준을 확인한 뒤에 `완료`로 바꿉니다. 실제로 배포한 경우에만 환경·커밋·시각·결과를 기록합니다.
5. 커밋 메시지와 PR 설명에는 관련 파일 경로(예: `docs/work/orchestrator/0001-…md`)를 적습니다. 변경 기록(`CHANGELOGS.md`)의 근거에도 같은 경로를 씁니다.
6. 에이전트에 위임할 때는 티켓 하나를 해당 `역할` agent에 맡기고, 에픽 단위 복합 작업은 `orchestrator`가 티켓 사이의 선행 관계와 통합 검증을 조정합니다.
7. 기술 설계를 거친 에픽은 `연결`에 설계 문서(`docs/specs/<에픽>.md`)와 PRD를 링크하고, 각 티켓의 `연결`에는 설계 문서의 해당 절과 담당 요구 번호(R1…)를 적습니다. 설계 내용은 work item에 복사하지 않습니다([기술 설계와 티켓 분해](../specs/README.md)).

## 착수와 점유

- **착수 가능**: 에픽이 아니고, 하위 항목이 없고, `상태: 준비`이며, 자신과 모든 상위의 `선행`이 `완료`이고, 아래 브랜치로 점유되지 않은 항목입니다. `pnpm work:next`가 우선순위(`(AI 제안)` 표시는 무시) → 번호 순으로 보여 줍니다.
- **점유는 브랜치입니다**: `work/NNNN-<파일 이름의 slug>` 브랜치(로컬 또는 원격)가 있으면 누군가 착수한 것입니다. 사람이든 에이전트든 착수할 때 먼저 이 브랜치를 만들고 그 브랜치에서 상태를 `진행`으로 커밋합니다. 점유를 기록하는 별도 파일은 없습니다. 병합하거나 버린 뒤 브랜치를 지우면 점유가 풀립니다.
- **여러 역할을 한 브랜치에 묶을 때**: 에픽의 여러 티켓을 한 브랜치·PR로 통합하면 브랜치 번호는 에픽이 아니라 그 에픽의 `orchestrator` 티켓(통합 티켓) 번호로 씁니다(`work/<통합 티켓 번호>-<slug>`). 에픽에는 `역할`이 없어 `pnpm work:scope`(CI `work scope`)가 실패하고, `orchestrator`는 모든 경로를 소유하기 때문입니다. 묶인 각 티켓의 상태·검증 기록은 각자의 파일에 남깁니다.
- **실행기**: `pnpm work:run`은 이 규칙대로 브랜치와 worktree를 만들고 루트 `WORKFLOW.md`의 프롬프트로 에이전트를 실행합니다. 에이전트가 상태를 `검증`(또는 `분류 대기`)으로 바꾸면 인계로 끝나고, `준비`·`진행`으로 남으면 재시도합니다. 자세한 동작은 [작업 실행기](../development/agent-runner.md)입니다.
- **에이전트가 발견한 일**: 에이전트는 맡은 범위 밖의 개선점이나 하네스에 빠진 능력(검사, 명령, 문서, 로그 등)을 직접 고치지 않고 새 work item으로 등록합니다. [TEMPLATE.md](TEMPLATE.md) 형식으로 모든 폴더를 통틀어 다음 빈 번호를 쓰고, 맡을 역할의 폴더(`docs/work/<역할>/`)에 두며, `상태: 분류 대기`, 우선순위 뒤에 `(AI 제안)`을 붙여 작업 브랜치에서 함께 커밋합니다. 사람이 분류할 때 우선순위를 확정하고 `(AI 제안)`을 지웁니다.
- **번호 충돌**: 병렬 브랜치에서 같은 번호를 쓰면 병합 후 `pnpm work:check`가 번호 중복으로 실패합니다. 나중에 병합하는 쪽이 다음 빈 번호로 파일 이름·제목 줄과 그 번호를 가리키는 `상위`·`선행`·링크를 고칩니다.

## GitHub Issues 개념과의 대응

| GitHub | 이 저장소 |
| --- | --- |
| Epic(상위 Issue) | `단계: 에픽` |
| Issue | `단계: 티켓` |
| Sub-issue | `단계: 하위 티켓` + `상위` |
| 진행률·트리 | `pnpm work` |
| Blocked by | `선행` |
| Assignee(착수 표시) | `work/NNNN-<slug>` 브랜치 |
| 라벨 | `종류`, `우선순위`, `역할` |
| Issue 양식 검증 | `pnpm work:check` |
| PR의 `Closes #N` | 같은 PR에서 work item 상태를 `완료`로 변경 |
