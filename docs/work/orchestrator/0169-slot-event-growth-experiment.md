# 0169 첫 크리링 완성 챌린지 기획과 자사 캠페인

## 목적

**첫 크리링 완성 챌린지**를 자사 공개 문서 경로에 구현합니다. “목적 고르기→직접 대표 링크 등록→본인의 프로필 공유 준비”의 자발적 3단계로 첫 가치를 경험하게 하는 안내입니다. 참여에 새 금전/경품 보상이나 외부 게시 의무를 걸지 않습니다. 기존 신청자 한정 슬롯 +5 이벤트(R24)는 실제 공개 API 상태를 확인한 뒤 별도 선택 혜택으로 소개하고 조건을 변경하지 않습니다. `0168` 편집기와 `0164` CTA는 수정하지 않으며 공통 결과 지표의 중복 영향은 기록합니다.

## 팀별 과제

- Events/Lifecycle: 현행 혜택·조건·자발적 신청·첫 링크 연결 시나리오.
- Growth/Marketing: 자사/외부 채널용 사실 기반 안내 소재. 무료 외부 게시와 비용 없는 보상 조건은 PM이 준수/접근·제품 계약으로 판단하며 지출/결제만 사람 승인으로 분리합니다.
- Product/Web: 신청에서 실제 링크 작성으로 이어지는 UX와 대안 비교.
- API/Data: 기존 한 번 신청·보너스 합산 계약과 측정 가능 지표 검토. 집계 공백을 사실로 보고.
- SRE/Security/QA: 출시/되돌림·보상 오표시·중복 신청·개인정보·권한 검토.

전담 `crelink-pm`이 팀별 조사·보고·실제 구현/홍보를 통합합니다. 무료 회사 계정·홍보 자체를 승인 대기로 두지 않습니다. 이 과제의 현재 범위를 넘는 새 추첨·개인정보 수집은 구현에 몰래 포함하지 않으며 지출/결제/비용 약정은 사전 사람 승인, 법·약관·동의·권한은 실행 조건으로 구분합니다.

워커 지시대로 build/lint/tests/formatter는 실행하지 않습니다. 이 checkout에는 `node_modules/next/dist/docs/`가 없어 공식 Next.js 16 안내와 기존 Server Component 패턴을 읽었습니다. 실제 390px/1280px 화면·API/DB·CI→guard→Deploy 검증은 PM이 통합 후 수행하며, 아래는 실행 결과가 아닌 정확한 시나리오입니다.

1. 이 커밋을 0168 변경과 통합할 때 `src/lib/docs.ts`·PRD·연구·두 로그의 추가 항목을 함께 보존합니다. `/me` 편집기·홈·공개 랜딩 CTA에 0169 변경이 없는지 확인합니다. `pnpm work:scope 0169`, `pnpm verify --fast`를 최종 한 번 실행합니다.
2. `make up` / `pnpm instance`로 localhost 웹·API·DB 주소를 확인합니다. `/docs` 목록·기존 `/docs/guide`의 문서 메뉴에서 **첫 크리링 완성 챌린지**를 열고 `/sitemap.xml`에 새 경로가 있는지 확인합니다.
3. 새 안내를 390px/1280px에서 열어 가로 넘침·콘솔 오류·키보드 초점을 확인합니다. Tab/Enter/Space로 세 목적 `summary`를 펼치고 2단계 앵커로 이동합니다. 네트워크에 공개 슬롯 GET 외 캠페인 쓰기/추적 요청이 없고 펼치기만으로 저장/신청되지 않아야 합니다.
4. 지표 제외 localhost 합성 계정으로 기존 홈 Google 시작의 개발 로그인 흐름→`/me` 편집기에 들어갑니다. 본인 시험 HTTP(S) URL·이름을 직접 입력하고 저장한 뒤 **공개 페이지 열기**로 실제 링크를 확인합니다. 미저장 미리보기만 보이는 상태·잘못된 URL·저장 API 오류·한도 찬 상태는 기존 오류 처리 그대로여야 합니다. 기본 한도는 5이며 첫 링크 작성에 이벤트 신청은 필요하지 않습니다.
5. 같은 합성 계정에서 단축 주소 **복사**를 실행하고 로컬 clipboard를 확인합니다. 주소는 기존 단축 URL이어야 하고 외부 프로필 게시/완료 제출을 요구하지 않아야 합니다. `/me`로 다시 이동해 기존 링크를 고칠 수 있어야 합니다.
6. localhost 운영자 화면만 사용해 기존 이벤트를 `open`→`scheduled`→`ended`로 바꾸며 새 안내를 새로고침합니다. 각각 실제 신청 가능/시작 전/종료 문구를 확인하고 종료 때 활성 신청 문구가 없어야 합니다. `open`에서 미신청 합성 계정의 명시적 신청 후 +5, 동일 계정 재신청 200/신청 행 1개, 종료 후 미신청 409·기존 보너스 유지·수동 슬롯 별도 합산을 기존 슬롯 API/DB 시나리오로 확인합니다. 이벤트 없음은 별도 격리 로컬 fixture, 네트워크/503은 로컬 API 중단으로 확인하며 오류를 `open`으로 대체하지 않아야 합니다. 공유 테스트 DB의 기간 변경은 직렬 실행하고 반드시 원래 기간을 복구합니다.
7. CI 성공→PM guard→main→Deploy→공개 확인 후 실제 시작/종료와 관측일·0164/0168 겹침을 기록합니다. 배포/공개를 워커 구현 완료와 혼동하지 않습니다. 오표시·저장/가입 회귀·개인정보/접근성 결함이면 새 경로/문서 등록을 revert하고 신청 행·보너스·사용자 링크는 보존합니다.
